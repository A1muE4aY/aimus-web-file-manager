# AWFM v0.1.2 接力开发任务书

## 0. 版本定位与执行原则

项目：AWFM（Aimu's Web File Manager）

当前基线：v0.1.1

目标版本：v0.1.2

本次更新定位：**维护与体验优化版本**。重点改善文件列表布局、统一启动方式、完善 SSH 配置教程，并核实、处理此前遗留的缺陷和未验证风险。

本次不以增加大型功能为目标，不应借机引入不必要的架构重构。

### 强制执行顺序

1. 检查工作区、Git 状态、现有文档、测试及发行包。
2. 盘点 v0.1.1 的已知限制、未验证项和可能遗留的真实缺陷。
3. 对遗留问题逐项判断优先级，先修复阻塞发布的缺陷。
4. 运行回归测试，确认修复没有破坏现有功能。
5. 优化文件列表布局。
6. 统一启动脚本为 `run.bat` 和 `run.sh`，完善交互提示与停止行为。
7. 编写全面、准确、可操作的 SSH 配置教程。
8. 执行自动化测试和真实桌面 CU 验收。
9. 更新版本、变更日志、用户文档、发行包和校验和。

**禁止先开发新功能、最后才处理遗留问题。** 每一阶段都应记录实际结果。若前置问题仍未解决，必须说明原因和风险，不得直接宣称全部完成。

## 一、阶段一：检查遗留问题与当前基线

### 1.1 检查项目状态

开始前检查：

- 当前分支、HEAD、工作区改动和未跟踪文件。
- `app/__init__.py` 中的版本号。
- `docs/CHANGELOG.md`、`docs/RELEASE.md`、`docs/USER_GUIDE.md`。
- `docs/reports/` 下的阶段六回归报告和 CU 验收报告。
- `scripts/test.py` 及各层测试目录。
- 现有启动脚本、停止脚本、启动器和发行包结构。
- v0.1.1 发行包的实际内容与 SHA-256 校验和。

不要覆盖 v0.1.1 的原始 CU 截图、操作轨迹、回归报告或发行包证据。

### 1.2 对遗留事项分类

逐项建立问题清单，区分：

- **已确认缺陷：** 可以复现，且实际行为不符合预期。
- **未验证风险：** 尚未在目标环境中验证，但可能影响可靠性或安全性。
- **已知限制：** 当前设计明确不支持的场景。
- **体验改进：** 不影响核心正确性，但影响易用性。

v0.1.1 报告中曾记录以下未验证事项，必须先复核其当前状态：

1. 虚拟机运行但 SSH 不可达。
2. 虚拟机 IP 变化、重复发现结果和扫描取消。
3. 接近文本编辑器大小上限的大文件。
4. 非 UTF-8 文件在真实界面中的提示。
5. 网络中断或虚拟机重启导致的被动掉线。
6. 发行包在独立目录和干净环境中的启动情况。

如果某项已经通过可靠测试验证，应更新状态并记录证据；如果仍有问题，应判断是否阻塞本次发布。不能仅因为它出现在旧报告中，就假定它必然是当前缺陷。

### 1.3 遗留问题修复门槛

- 修复所有已确认的高优先级缺陷。
- 对影响安全、文件完整性、权限控制或发行包启动的问题，必须优先处理。
- 对无法在本轮解决的事项，说明原因、影响范围、规避方案及是否允许发布。
- 为每个已修复缺陷增加或完善回归测试。
- 完成阶段性回归后，再进入本轮体验优化。

不得通过删除测试、弱化断言、跳过失败项或更改测试预期来制造全绿结果。

## 二、阶段二：文件列表布局优化

### 2.1 目标

当前文件列表存在操作按钮拥挤、排序和对齐不一致的问题。允许牺牲部分超长文件名的横向显示空间，优先保证表格结构稳定、按钮位置固定、交互容易识别。

### 2.2 布局要求

检查当前文件列表的 HTML 结构、CSS 样式及相关 JavaScript 渲染逻辑，采用明确、统一的列布局。

建议的列结构：

| 列 | 布局原则 |
|---|---|
| 名称 | 占据主要可用空间，允许收缩 |
| 大小 | 固定或受控宽度，数值对齐 |
| 类型 | 固定或受控宽度 |
| 权限 | 固定或受控宽度 |
| 修改时间 | 固定或受控宽度，避免日期格式导致错位 |
| 操作 | 固定宽度，按钮统一对齐 |

以上是建议结构，最终应依据当前实际功能调整，不能因为表格拥挤而删除必要信息。

具体要求：

- 同一列的按钮位置必须保持一致。
- 文件行的按钮不能因为文件名长短、文件类型或图标差异而左右移动。
- 同类按钮的尺寸、间距、对齐方式和视觉层级保持一致。
- 操作区域应具有明确的固定宽度或受控宽度。
- 优先使用稳定的表格布局、CSS Grid 或现有组件体系，避免依赖脆弱的手动空格和随机边距。
- 不要让操作按钮覆盖文件名、大小、权限或修改时间。
- 保持键盘操作、焦点状态和按钮可访问性。
- 不要为了对齐而无差别缩小所有文字。

### 2.3 超长文件名的展示方案

超长文件名允许在列表中截断，但不能丢失用户获取完整名称的途径。

必须实现至少一种可靠的完整名称查看方式，建议同时实现以下方式：

1. **悬浮提示：** 鼠标悬停在被截断的名称上时，显示完整文件名。
2. **完整名称查看：** 通过文件名链接、详情区域或可访问的提示组件查看完整名称。
3. **复制名称：** 如果当前交互结构适合，可以增加复制完整文件名的操作；如果增加，必须有成功或失败反馈。

要求：

- 截断只能影响视觉显示，不得修改真实路径、请求参数、上传文件名或编辑文件名。
- 中文、英文、空格、括号、长扩展名和特殊字符应正确处理。
- 不要把完整路径与文件名混淆；必要时分别显示。
- 鼠标悬浮不是唯一访问方式，键盘用户也应能查看完整名称。
- 对根本无法显示完整名称的窄窗口，应提供明确的查看方式，而不是让名称覆盖其他列。

### 2.4 验收场景

至少检查：

- 普通短文件名。
- 很长的英文文件名。
- 很长的中文文件名。
- 带空格和括号的文件名。
- 不同文件类型及目录行。
- 0 字节文件和大文件。
- 多种权限字符串。
- 不同长度的修改时间显示。
- 窗口变窄、变宽及浏览器缩放。
- 鼠标悬停、键盘焦点和按钮点击。

使用真实桌面 CU 截图记录优化前后的差异。不得仅凭 CSS 测试或 DOM 检查宣称布局验收通过。

### 2.5 自定义右键菜单与交互扩展

#### 目标

禁止 AWFM 应用内容区域内的浏览器原生右键菜单，建立统一的自定义上下文菜单机制，为后续文件操作扩展提供基础。

#### 实现要求

- 在 AWFM 的文件列表及连接卡片等适合扩展操作的区域，拦截鼠标右键触发的浏览器原生上下文菜单。
- 通过 `contextmenu` 事件实现自定义菜单入口，不得通过全局操作系统设置或浏览器配置禁用右键。
- 自定义菜单应根据右键目标及当前状态显示对应操作，不应对所有对象显示相同的无效选项。
- 文件列表中的菜单至少应能识别文件与目录，并获取对应条目的真实路径、名称及类型。
- 菜单位置应根据鼠标位置动态确定，避免超出浏览器视口；靠近屏幕边缘时应自动调整位置。
- 菜单应具有清晰的视觉层级、悬停状态、焦点状态和禁用状态，并与 AWFM 当前主题保持一致。
- 点击菜单外部、按下 `Escape` 或切换目录时，应按合理规则关闭菜单。
- 菜单打开后应支持基本键盘操作，不能完全依赖鼠标。
- 不得因为右键菜单拦截而影响文本选择、文件名复制、输入框编辑、浏览器地址栏、开发者工具或应用外部的正常右键行为。
- 对文本输入框、文本编辑器、可编辑区域等，应保留合理的原生文本编辑交互；如果某个区域确实需要自定义菜单，必须先定义相应的替代操作，不能直接破坏复制、粘贴等基本功能。
- 右键菜单只负责提供操作入口；每项操作仍须调用现有业务逻辑，并遵循既有权限检查、错误处理和确认流程。
- 不得仅在前端隐藏菜单就宣称操作受到安全保护。服务端必须继续独立验证权限。

#### 第一阶段交付范围

本次先建立稳定的自定义上下文菜单框架，并接入已经存在、适合放入菜单的操作。不要为了填满菜单而新增未经设计的文件操作。

对于尚未实现的复制、剪切、重命名、删除、下载等功能，不得显示看似可用但实际无效的菜单项。若需要为后续版本预留扩展接口，应确保接口清晰，但不必在本次实现所有扩展功能。

#### 验收要求

1. 在文件和目录上右键时，不再显示浏览器原生上下文菜单。
2. 自定义菜单能正确识别右键目标，不会错误地对相邻文件执行操作。
3. 在视口四周打开菜单时，菜单不会被裁切。
4. 点击空白区域、按 `Escape` 或切换目录后，菜单能正确关闭。
5. 文本编辑器、输入框中的复制、粘贴和文本选择仍然正常。
6. 菜单中的操作遵循现有写权限及服务端安全校验。
7. 使用真实桌面 CU 验证鼠标右键、菜单定位、关闭行为及基本键盘交互，并保留截图证据。

#### 后续扩展方向

后续可在此机制中逐步增加文件预览、编辑、下载、复制路径等操作。剪切、粘贴、重命名、删除等会改变远端文件状态的操作，应在独立设计并完成权限与安全评估后再加入。

## 三、阶段三：统一启动脚本

### 3.1 目标

当前使用 `start.cmd` 和 `stop.cmd` 分别启动、停止服务，用户需要理解多个入口，提示信息也不够充分。

改为统一的启动入口：

- Windows：`run.bat`
- Linux：`run.sh`

**正常使用时，用户只需要执行对应平台的 `run` 脚本。**

### 3.2 先检查现有启动逻辑

开始修改前，检查现有脚本及其调用的 Python 启动器，确认：

- 服务进程如何启动。
- 是否存在后台进程或 PID 文件。
- 停止脚本目前如何定位并终止进程。
- 如何检测服务是否已经运行。
- 如何处理端口冲突、Python 缺失、配置错误和 SSH 依赖缺失。
- 关闭终端窗口是否会导致服务意外退出。
- 便携发行包中的工作目录、配置目录、日志目录如何确定。

不要简单地将 `start.cmd` 重命名为 `run.bat`、把 `stop.cmd` 重命名为 `run.sh`，也不要假定 Windows 与 Linux 的进程管理方式完全相同。

### 3.3 `run.bat` 行为

Windows 用户执行 `run.bat` 后，应当：

1. 切换到脚本所在的项目或发行包目录，避免依赖当前终端工作目录。
2. 检查 Python 版本及必要的系统 OpenSSH 客户端。
3. 检查配置文件、数据目录和日志目录。
4. 检测服务是否已运行，避免重复启动。
5. 检查监听地址和端口是否可用。
6. 启动服务并报告实际结果。
7. 在适当情况下打开默认浏览器，或清楚地提示访问地址。
8. 提供清晰的运行状态、日志位置和停止方法。

发生错误时，必须显示具体原因及建议操作，不能只闪退或留下无法理解的 Python traceback。

### 3.4 `run.sh` 行为

Linux 用户执行 `./run.sh` 后，应实现与 Windows 版本相同的用户目标：

- 检查 Python、OpenSSH 及必要环境。
- 确定正确的工作目录。
- 检查配置、数据目录、日志目录及监听端口。
- 防止重复启动。
- 清晰显示服务地址和运行状态。
- 提示如何查看日志、停止服务及处理常见错误。

脚本应使用可靠的 Shell 写法，处理空格路径和执行失败。不要依赖未声明的第三方命令。

### 3.5 启动与停止的统一设计

优先使用同一入口提供简单的交互菜单，例如：

- 启动服务。
- 查看运行状态。
- 停止服务。
- 查看日志。
- 退出。

也可以根据当前架构采用命令参数，但必须保持清晰、一致，并在启动时展示使用方式。

无论采用菜单还是参数，都必须满足：

- 首次使用者能够看懂如何启动、访问和停止服务。
- 已运行时不会重复启动第二个服务实例。
- 停止操作只作用于 AWFM 自己管理的进程，不得误杀其他 Python 或 SSH 进程。
- 停止失败时说明原因，并提供安全的人工处理方式。
- 不得未经用户确认就使用强制终止。
- 如果服务在终端前台运行，应明确提示使用 Ctrl+C 停止；如果后台运行，应明确告知如何通过统一入口停止。
- 对服务启动失败、端口被占用、配置文件损坏和权限不足等情况，提供可理解的错误提示。
- 不得因为脚本执行结束就错误地宣称服务已经成功启动或停止。

### 3.6 兼容性和交付要求

- 检查 README、用户指南、发布说明、安装说明和发行包内的所有脚本引用。
- 将正常使用说明统一改为 `run.bat` / `run.sh`。
- 如果旧版 `start.cmd`、`stop.cmd` 有必要保留兼容层，应明确标注弃用状态及迁移方式；否则从新发行包中移除。
- 不要留下多个互相矛盾的启动入口。
- 确保发行包中的脚本实际存在，引用的路径和配置文件正确。
- 测试从包含空格的目录路径启动。
- 测试重复启动、停止、再次启动及端口冲突。
- 为了避免占用，请将默认端口改为'32579'。

### 3.7 真实验收

在 Windows 上真实运行 `run.bat`，确认：

1. 首次启动成功。
2. 已运行时重复执行会给出正确提示。
3. 浏览器能访问正确的本地服务地址。
4. 停止操作不会误终止其他进程。
5. 停止后再次启动正常。
6. 缺少依赖或端口被占用时提示清晰。

如果当前环境存在 Linux 测试环境，使用真实 `run.sh` 进行对应验收。若没有，则记录未验证项，不得用模拟 Shell 输出冒充真实 Linux 测试。

## 四、阶段四：编写全面的 SSH 配置教程

### 4.1 文档目标

新增或重构 SSH 配置教程，建议文件名为：

`docs/SSH_SETUP_GUIDE.md`

同时在 `docs/USER_GUIDE.md` 中增加清晰的入口链接。

教程应覆盖从零开始配置 SSH 的用户，也应帮助已有 SSH 使用经验的用户排查连接问题。

文档应采用循序渐进的结构，并为 Windows、常见 Linux 发行版以及不同虚拟化环境提供相应分支。

不得把仅适用于某个操作系统的命令写成通用命令。每条命令都应说明执行位置、适用系统、所需权限和预期结果。

### 4.2 建议章节

#### A. SSH 基本概念

用简明语言解释：

- SSH 客户端与服务端的区别。
- 主机名、IP 地址、端口、用户名和认证方式的含义。
- 公钥与私钥的区别。
- SSH 主机指纹的作用。
- AWFM 如何通过系统 OpenSSH 建立连接并使用 SFTP 传输文件。
- 为什么 SSH 服务可达不代表身份认证一定成功。

明确说明：AWFM 本身不是 SSH 服务端，不会替用户自动安装或启动远端 SSH 服务。

#### B. 连接前的检查清单

指导用户确认：

- 远端主机正在运行。
- 已知远端正确的 IP 地址或主机名。
- 已确认目标登录用户名。
- SSH 服务端已安装并运行。
- 防火墙与网络路由允许访问目标端口。
- 客户端拥有适用的 SSH 工具。
- 用户知道应该使用密码认证还是密钥认证。

区分虚拟机控制台登录、Linux 本地账户登录与远程 SSH 登录；三者不能默认等价。

#### C. Linux SSH 服务端配置

分别介绍常见发行版的配置差异，例如：

- Ubuntu / Debian。
- CentOS Stream / RHEL 系。
- Fedora 或其他使用 systemd 的发行版。

说明如何：

- 检查 OpenSSH Server 是否安装。
- 安装缺失的软件包。
- 查看 `sshd` 服务状态。
- 启动并启用服务。
- 检查 SSH 监听端口。
- 查看服务端日志。
- 检查 `sshd_config` 中的关键选项。
- 修改配置后验证语法并安全重载服务。

重要要求：

- 不要要求用户不加判断地覆盖整个 `sshd_config`。
- 修改 SSH 端口、认证方式或登录策略前，先备份配置并说明风险。
- 在修改远程访问设置前，提醒用户保留当前可用的控制台或 SSH 会话。
- 不得建议直接关闭防火墙或关闭 SELinux 来解决所有连接问题。
- 需要修改防火墙规则时，应明确限定目标端口、网络范围及适用平台。
- 命令必须根据实际发行版和服务名称区分。

#### D. Windows SSH 客户端

介绍 Windows OpenSSH Client 的检查方法：

- 使用 `ssh -V` 查看客户端版本。
- 使用 `where ssh` 检查程序路径。
- 通过 `ssh username@host` 进行基础连接测试。
- 通过 `ssh -p PORT username@host` 指定端口。
- 使用 `ssh -v` 或适当的详细日志排查问题。
- 检查 `%USERPROFILE%\.ssh\` 中的配置和密钥文件。
- 说明 Windows 文件权限可能影响私钥使用。

不要假设所有 Windows 机器都已经安装 OpenSSH Client，也不要要求用户下载来源不明的 SSH 工具。

#### E. Linux SSH 客户端

说明：

- 检查 OpenSSH Client 是否安装。
- 使用 `ssh user@host` 测试连接。
- 使用 `ssh -p PORT user@host` 指定端口。
- 使用 `ssh -v` 排查认证和连接问题。
- 检查 `~/.ssh/config`、`known_hosts` 和私钥权限。
- 说明不同 Shell 和发行版的路径、权限差异。

#### F. 密码认证

说明密码认证的使用条件、服务端配置要求及安全注意事项。

必须提醒用户：

- 密码必须由用户本人输入，不应写入脚本、源代码或日志。
- 不要猜测密码或自动尝试多个账户。
- AWFM 不应通过扫描文件、历史记录或日志寻找用户密码。
- 如果服务端禁用了密码认证，应解释如何通过受控的管理渠道确认配置，而不是鼓励盲目修改安全策略。
- 如果当前产品仅支持特定认证方式，应以实际实现为准，不得虚构功能。

#### G. SSH 密钥认证

完整说明：

1. 检查是否已有可用密钥。
2. 在客户端生成密钥对。
3. 选择合理的密钥算法，并说明兼容性差异。
4. 设置可选的私钥口令。
5. 将公钥安全地安装到目标账户。
6. 检查远端 `~/.ssh` 和 `authorized_keys` 权限。
7. 使用 `ssh -i` 指定私钥测试登录。
8. 使用 `ssh-add` / `ssh-agent` 的适用场景。
9. 验证 AWFM 所使用的私钥路径与命令行测试一致。

提供 Windows PowerShell 与 Linux Shell 的对应命令示例。

不得将私钥内容粘贴到 AWFM 配置、聊天记录、日志或公开文档中。公钥和私钥必须明确区分。

#### H. VMware、虚拟机网络与远程连接

- 虚拟机处于运行状态，不代表 SSH 已启动。
- NAT、桥接、仅主机网络的基本差异。
- 如何从客户机确认 IP 地址。
- 如何判断客户端能否到达该 IP。

- 私钥路径或密码输入方式（以实际支持为准）。

#### J. 常见错误与诊断流程

至少覆盖：

- `Connection refused`
- `Connection timed out`
- `No route to host`
- `Permission denied (publickey,password)`
- `Host key verification failed`
- 主机指纹变化。
- 私钥文件无法读取或权限过宽。
- SSH 服务未启动或监听在错误端口。
- 远端用户名错误。
- SFTP 子系统不可用。
- 连接成功但无法列出目录。
- 文件权限不足或家目录不可访问。
- 网络中断导致连接失效。

每种错误应包括：

1. 可能原因。
2. 推荐检查顺序。
3. 对应命令。
4. 如何判断检查结果。
5. 安全的修复方向。

不要把所有错误都归因于防火墙。

#### K. 安全建议与维护

包括：

- 私钥保管。
- 主机指纹核验。
- 最小权限原则。
- 合理设置 SSH 访问范围。
- 备份 SSH 配置。
- 定期更新系统。
- 日志与敏感信息保护。
- 连接配置文件的访问权限。
- 不使用未知来源的脚本自动配置 SSH。

#### L. 快速排查清单

在教程末尾提供一页式检查表，帮助用户按以下顺序定位问题：

网络可达 → SSH 端口可达 → 服务端正常 → 用户名正确 → 认证成功 → 主机指纹可信 → SFTP 可用 → 目录权限正确。
