# AWFM v0.1.3 接力开发任务书

**版本：** v0.1.3  
**基线版本：** v0.1.2  
**更新类型：** 紧急体验修复与功能补齐  
**核心目标：** 修复文件列表布局问题、改善预览框、增加创建文件功能，并重新梳理普通启动与高级启动脚本。

## 0. 执行优先级与强制规则

本次以修复现有问题为第一优先级，不得在未检查现有代码、测试和报告前直接开始堆叠功能。

### 第一优先级：已有问题修复

1. 阅读 v0.1.2 最新开发报告、回归报告、CU 验收报告及遗留问题清单。
2. 找出报告中已经确认、会影响正常使用的问题。
3. 对已确认的功能缺陷、界面错误、数据完整性问题和安全问题优先修复。
4. 对明确记录为暂不影响使用的问题，可结合本轮修改范围判断是否处理。
5. 对尚未验证的场景，记录验证状态，不要直接将其描述为已发现的缺陷，也不要求为了本次更新而穷尽所有未验证场景。

若发现可能导致远端文件丢失、意外覆盖、权限绕过或服务无法启动的问题，必须先处理。

### 第二优先级：本次五项需求

1. 文件操作按钮布局重构。
2. 文件信息区域布局重构。
3. 文件预览增加独立容器框。
4. 增加创建文件功能。
5. 将启动脚本划分为普通启动和高级启动，并让两者都能在启动成功后打开默认浏览器。

### 第三优先级：回归、真实 CU 验收和发行包

所有功能完成后，再运行完整测试、进行真实桌面验收并构建 v0.1.3 发行包。

不得通过删除测试、降低断言要求、跳过失败项或只检查静态代码来宣称完成。

## 一、文件操作按钮：建立独立操作区域

### 1.1 当前问题

参考用户提供的 v0.1.2 截图：

- 操作按钮的文字垂直对齐不自然。
- 按钮宽度和间距不统一。
- 不同行的按钮因可用操作不同而发生错位。
- 文件名区域与操作区域的空间分配不合理。
- 顶部“操作”标题没有与按钮区域统一居中。

### 1.2 布局方案

为操作列建立独立的布局容器，例如 `file-actions-box`，不得继续依赖零散的内联样式或手动调整边距。

要求：

- 操作列具有明确的固定或受控宽度。
- 列标题“操作”在整个操作列内水平居中。
- 每一行的操作区域宽度一致。
- 所有按钮的高度、字体、文字基线、圆角和间距保持一致。
- 按钮文字水平、垂直居中。
- 不同文件类型对应的操作数量可以不同，但按钮的位置必须按照统一规则排列。
- 文件名变长时，应优先截断文件名，而不是挤压或推动操作按钮。
- 不允许按钮覆盖文件名、文件大小、权限或修改时间。
- 保持现有深色主题和 AWFM 整体视觉风格。

### 1.3 按钮顺序

统一采用以下顺序：

1. 编辑
2. 复制
3. 剪切
4. 重命名
5. 删除
6. 压缩
7. 解压

五个按钮在同一操作区域内横向排列，不得因为文件类型不同而改变剩余按钮的相对顺序。

不同文件类型的按钮规则：

- **可编辑文本文件：** 显示“编辑”。
- **不可编辑的二进制文件：** 不显示可用的编辑按钮；如果用户尝试编辑，应沿用现有的明确提示方式，说明该文件无法通过文本编辑器处理。
- **可压缩文件或普通文件：** 根据现有压缩实现与后端能力决定是否显示“压缩”。
- **可解压文件：** 显示“解压”。
- **不可解压文件：** 不应让解压操作以错误方式执行。若用户尝试解压，应与不可编辑的二进制文件保持一致的交互原则，明确提示文件无法解压，并说明原因。

不得仅通过扩展名就宣称一个文件一定可解压。应以实际支持的格式和后端校验结果为准。

对于不适用的操作，可采用统一的禁用状态，也可隐藏按钮；应根据当前产品设计选择一种一致的策略。无论采用哪种方式，都不能导致其他按钮的位置跳动。

### 1.4 固定位置策略

优先采用 CSS Grid 或稳定的表格布局，为操作列分配独立空间。

如果五个按钮在当前窗口宽度下无法合理容纳，应优先调整文件名列和其他可弹性列，不得让按钮文字相互挤压。

如果仍然无法容纳，应采用明确的最小窗口宽度或合理的横向滚动方案，而不是让操作列崩坏。

## 二、文件信息：建立独立信息区域

### 2.1 当前问题

截图显示文件名称、大小、类型、权限、修改时间及操作列之间的对齐不够稳定，整体显得拥挤。

### 2.2 改造要求

为每个文件行建立独立的信息布局容器，建议采用稳定的 CSS Grid 或表格列定义。

列结构：

| 列 | 要求 |
|---|---|
| 名称 | 占用主要弹性空间，可截断显示 |
| 大小 | 固定或受控宽度，统一对齐 |
| 类型 | 固定或受控宽度 |
| 权限 | 固定或受控宽度，保持等宽字符的可读性 |
| 修改时间 | 固定或受控宽度，避免日期长度导致错位 |
| 操作 | 与第一阶段的独立操作区域一致 |

具体要求：

- 表头和每一行必须使用相同的列定义。
- 文件名截断不能改变实际文件名或路径。
- 大小、类型、权限、修改时间不得随内容长度而任意漂移。
- 文件名允许使用省略号显示，但必须有办法查看完整名称。
- 中文、英文、空格、括号和长扩展名均应正常显示。
- 不得因布局优化而丢失权限、文件大小、时间等现有信息。
- 对目录、普通文件、特殊文件等不同条目，应保持布局一致。
- 在合理窗口宽度下，不应出现水平错位、文字覆盖或按钮溢出。

文件信息容器与操作容器应有明确的职责边界，避免后续新增操作时再次破坏表格布局。

## 三、文件预览：增加独立预览框

### 3.1 目标

目前预览内容缺少明确的容器边界。本次应为预览区域增加独立、清晰的框体，让内容与背景、工具栏及其他页面元素区分开。

### 3.2 设计要求

- 预览内容放入独立的预览容器。
- 容器具有统一的边框、内边距、背景和圆角，与 AWFM 深色主题一致。
- 文件名、文件类型或预览状态应与正文内容区分。
- 长文本不得撑破容器。
- 超长内容应在容器内部滚动，而不是撑大整个页面。
- 预览框应适应当前窗口大小。
- 对代码或纯文本预览，应保留换行、缩进和可读性。
- 对二进制文件或不支持的格式，应使用现有错误提示机制说明无法预览。
- 预览框的改造不得绕过服务端文件访问权限检查。
- 不得为了显示预览而将完整大文件无条件加载到浏览器内存。

如果当前预览功能已经采用模态框，应在现有模态框内部建立独立内容框，不要重复叠加多个互相冲突的外层框。

### 3.3 验收场景

- 短文本文件。
- 长文本文件。
- 包含中文、空行和缩进的文件。
- 不支持预览的二进制文件。
- 预览内容超出容器高度。
- 关闭预览后重新打开其他文件。

## 四、增加创建文件、文件夹、多选功能

### 4.1 目标

允许用户在当前远端目录下创建新的空文件，并在成功后立即看到新文件。

### 4.2 用户交互

在当前目录工具栏中增加“新建文件”、“新建文件夹”、“多选”入口。

点击后分别打开简洁的创建对话框，至少包括：

- 文件名、文件夹名输入框。
- 创建按钮。
- 取消按钮。
- 清晰的校验或错误提示。

用户确认创建后，应在当前目录下创建文件，而不是跳转到其他目录。

对于多选，需要在单个文件行的最左边显示复选框，且能实现复制、剪切、压缩、解压、删除功能，对于具体限制请按照系统多选的逻辑进行约束。

### 4.3 文件名与路径安全

- 文件名必须是单个合法文件名，不能被解释为任意路径。
- 拒绝空名称、`.`、`..`、路径分隔符及当前平台不允许的文件名。
- 不允许用户通过 `../` 等方式越出当前目录。
- 文件名中的空格、中文和常见标点应在系统允许范围内正常处理。
- 对已存在的文件，默认拒绝创建，不得静默覆盖。
- 应使用安全的文件创建方式，例如具备排他创建语义的方式，避免“先检查不存在，再创建”导致的竞态覆盖。
- 服务端必须重新验证用户权限与目标路径。
- 前端禁用按钮不等于安全控制，后端必须独立校验。
- 失败时不得返回成功提示或假装文件已经创建。

### 4.4 权限规则

- 只有当前连接允许写操作且远端目录具有实际创建权限时，才允许创建。
- 如果当前连接禁止写操作，前端应禁用或隐藏创建入口。
- 即使前端未正确禁用，后端也必须拒绝越权请求。
- 创建成功后刷新当前目录，并显示成功反馈。
- 如果刷新失败，应明确区分“文件创建成功”和“目录刷新失败”，避免用户重复创建。

### 4.5 验收场景

1. 创建普通空文件。
2. 创建中文文件名。
3. 创建带空格的文件名。
4. 输入空文件名。
5. 输入带路径分隔符的名称。
6. 创建已存在的文件。
7. 远端目录不可写时创建。
8. 连接断开时创建。
9. 当前连接禁止写操作时创建。
10. 创建成功后刷新列表，确认文件真实存在且大小为零。

## 五、启动脚本：普通启动与高级启动

### 5.1 目标

现有脚本保留为高级启动脚本，新增普通启动脚本。用户可以根据需要选择：

- 普通启动：一键启动服务，尽量不要求用户理解内部参数。
- 高级启动：保留现有脚本提供的高级控制、诊断或参数配置能力。

具体脚本文件名应结合当前项目结构统一确定，并在最终报告中明确列出。不要在未检查现有脚本之前随意覆盖或删除原有功能。

建议命名：

- Windows 普通启动：`run.bat`
- Linux 普通启动：`run.sh`
- Windows 高级启动：`run-advanced.bat`
- Linux 高级启动：`run-advanced.sh`

如果现有高级脚本已有稳定名称，可保留并在文档中说明；不得出现多个名称相似、行为却不一致的入口。

### 5.2 普通启动脚本

普通启动脚本应尽可能做到：

1. 自动切换到脚本所在目录。
2. 检查必要运行环境。
3. 使用默认配置启动 AWFM。
4. 防止重复启动。
5. 等待服务真正就绪后，再使用用户的默认浏览器打开 AWFM 页面。
6. 明确显示服务地址、启动结果、日志位置和停止方法。
7. 出错时保持窗口可读，不应一闪而过。

普通启动脚本不应要求用户理解 Python 参数、监听地址、调试选项或内部目录结构。

### 5.3 高级启动脚本

高级启动脚本应保留并整理现有高级能力，例如：

- 指定监听地址或端口。
- 查看或调整启动参数。
- 诊断运行环境。
- 查看服务状态或日志。
- 按项目已有设计执行安全的停止或重启操作。

只保留当前确实存在、经过验证且有价值的能力，不得在文档中虚构高级选项。

高级启动脚本同样必须具备以下功能：

**当服务真正启动并确认就绪后，自动使用用户默认浏览器打开页面。**

如果用户主动选择不自动打开浏览器，可通过明确的参数或选项关闭此行为；但默认行为必须符合本任务要求。

### 5.4 默认浏览器打开逻辑

Windows 与 Linux 应分别使用适合平台的方式调用默认浏览器，例如 Windows 的系统默认 URL 打开机制，以及 Linux 的 `xdg-open` 或当前桌面环境可用的默认打开机制。

要求：

- 不能硬编码 Edge、Chrome、Firefox 等某个浏览器。
- 必须在服务确认就绪后再打开页面。
- 不能仅因为启动命令返回了进程 ID 就宣称服务已经就绪。
- 浏览器打开失败时，应显示页面地址，让用户可以手动访问。
- 浏览器打开动作失败不能误报为服务启动失败。
- 如果环境没有图形桌面或默认浏览器，服务仍应能正常运行并输出访问地址。
- 不得无限等待服务就绪；应设置合理超时并给出诊断信息。
- 不得重复执行浏览器打开动作导致多个标签页不断弹出。

### 5.5 进程与停止行为

- 必须准确识别 AWFM 自己的服务进程。
- 不得通过无差别终止所有 `python.exe`、`python` 或 SSH 进程的方式停止服务。
- 已运行时再次启动，应显示清晰提示并提供当前访问地址。
- 高级脚本的停止或重启操作不得影响其他应用。
- 对停止失败、端口占用或配置错误，显示明确原因及安全的处理建议。

## 六、回归测试与真实 CU 验收

### 6.1 自动化测试

完成开发后，运行项目现有完整测试入口及必要的静态检查。

新增测试至少覆盖：

- 文件列表布局所依赖的前端逻辑。
- 不同文件类型的操作映射与按钮顺序。
- 创建文件的路径校验、重名拒绝和权限拒绝。
- 创建文件失败与连接断开的错误处理。
- 启动脚本的参数、状态检测和重复启动行为。
- 服务就绪判断和浏览器打开失败的处理。
- 预览容器的内容溢出及错误状态。

不要用自动化测试通过替代真实桌面交互验收。

### 6.2 真实桌面 CU

使用真实桌面和浏览器进行以下验收：

1. 启动 v0.1.3，确认版本显示正确。
2. 检查五个操作按钮是否按指定顺序排列、字体居中、位置固定。
3. 检查不同文件类型下的操作区域是否一致。
4. 检查文件信息列和表头是否对齐。
5. 检查长文件名是否正确截断且能够查看完整名称。
6. 打开文本预览，检查独立预览框和滚动行为。
7. 打开不支持的二进制文件，确认提示明确。
8. 创建空文件，检查列表和远端真实文件是否一致。
9. 在无写权限的情况下尝试创建文件，确认服务端拒绝。
10. 使用普通启动脚本启动，确认浏览器自动打开。
11. 使用高级启动脚本启动，确认浏览器同样自动打开。
12. 检查服务启动失败时是否显示明确错误信息。
13. 检查服务重复启动时是否正确处理。
14. 停止服务并再次启动，确认没有残留进程或端口冲突。

真实 CU 必须保留关键截图和操作记录。可以使用终端核对文件内容、大小、权限和进程状态，但不能用终端操作替代需要验证的界面交互。
